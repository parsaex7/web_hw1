## ۱. اجرای سرویس فقط روی شبکه داخلی

سرویس قدیمی برای آدم‌های داخل سازمان نوشته شده و خودش authentication ندارد. تا وقتی از اینترنت به پورتش نتوان وصل شد، این موضوع مشکل امنیتی نیست. پس اجرا روی شبکه داخل یعنی پروسه روشن باشد، ولی از بیرون یک اتصال TCP به آن پورت برقرار نشود.

برای این کار سرویس را به آدرسی bind می‌کنم که سمت اینترنت نیست. اگر فقط خود ماشین لازم دارد به آن وصل شود، `127.0.0.1` کافی است. اگر چند ماشین داخل سازمان باید ببینندش، یک IP خصوصی مثل رنج `10.0.0.0/8` یا `192.168.0.0/16`. فرق این با `0.0.0.0` این است که در حالت دوم برنامه روی همه کارت‌های شبکه گوش می‌دهد، از جمله کارتی که به اینترنت وصل است.

در داکر همین ایده با شبکه جدا پیاده می‌شود. `go-httpbin` را می‌گذارم روی یک شبکه داخلی و پورت ۸۰۸۱ را publish نمی‌کنم. فقط پروکسی عضو همان شبکه است و می‌تواند به آن برسد. از بیرون تنها پورت ۸۰ خود پروکسی باز است. اگر لازم باشد محکم‌تر شود، فایروال هم پورت ۸۰۸۱ را فقط برای IP پروکسی باز می‌گذارد و بقیه را می‌بندد.

## ۲. TLS Termination

سرویس legacy فقط HTTP حرف می‌زند. نه گواهی دارد، نه TLS را می‌فهمد. اگر همان را بگذاریم روی اینترنت، درخواست متن خوانا است. هدر `Authorization` و بقیه بدنه‌اش را هر کسی که وسط مسیر باشد می‌تواند ببیند یا عوض کند.

TLS Termination یعنی این رمزنگاری سر مرز شبکه، روی reverse proxy، تمام شود. کاربر با پروکسی HTTPS صحبت می‌کند و گواهی دست پروکسی است. پروکسی ترافیک را باز می‌کند، JWT را همان‌جا نگاه می‌کند، و بعد چون مسیر تا سرویس قدیمی داخل شبکه خودمان است، درخواست را با HTTP معمولی به پورت ۸۰۸۱ می‌فرستد.

دلیلش این است که قسمت ناامن مسیر اینترنت است، نه LAN سازمان. لازم نیست برنامه قدیمی را برای TLS دستکاری کنیم و گواهی هم فقط یک جا نگهداری می‌شود. برای خود این تمرین یک نکته دیگر هم هست: پروکسی باید توکن را بخواند. اگر تونل TLS تا خود httpbin می‌رفت، پروکسی محتوای درخواست را نمی‌دید و نمی‌توانست امضای JWT را چک کند.

## ۳. پروکسی

کد پروکسی `main.go` است. با `docker compose up --build` دو کانتینر بالا می‌آید.

`httpbin` همان سرویس قدیمی است و فقط به شبکه `inside` وصل است. این شبکه خروجی به اینترنت ندارد و پورت ۸۰۸۱ هم publish نشده، برای همین از سیستم خودم به آن پورت وصل نمی‌شوم. پروکسی عضو `inside` است تا به `http://httpbin:8081` برسد، و عضو شبکه `edge` هم هست تا پورت ۸۰ از بیرون باز باشد.

`/auth/login` مال خود پروکسی است و به httpbin نمی‌رسد. با این مسیر توکن می‌گیرم. برای بقیه مسیرها، اگر هدر `Authorization: Bearer` نباشد یا امضا نخورد یا `exp` گذشته باشد، پروکسی `401` می‌دهد و درخواست را جلو نمی‌فرستد. اگر توکن درست باشد، هدر `Authorization` را برمی‌دارد، اسم کاربر را در `X-Forwarded-User` می‌گذارد و درخواست را به سرویس قدیمی می‌فرستد.

نام کاربری دمو `parsa` و رمز `letmein` است. این رمز فقط برای همین تمرین است و جای دیگری استفاده نمی‌شود.

گرفتن توکن:

```bash
curl -s -X POST http://localhost/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"parsa","password":"letmein"}'
```

بدون توکن باید `401` برگردد:

```bash
curl -i http://localhost/get
```

با توکن، به‌جای `TOKEN` همان رشته‌ای که login داد:

```bash
curl -s http://localhost/get -H "Authorization: Bearer TOKEN"
```

اگر پورت ۸۰ اشغال باشد، در `docker-compose.yml` نگاشت `80:80` را به `8080:80` تغییر می‌دهم و به `localhost:8080` درخواست می‌زنم. سرویس قدیمی همچنان از بیرون در دسترس نیست.
