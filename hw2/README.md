## سؤال ۱

**تفاوت نسخه‌های HTTP:**

- **HTTP/0.9:** فقط متد `GET`، بدون Header و Status Code؛ مناسب دریافت صفحات HTML ساده.
- **HTTP/1.0:** اضافه‌شدن Header، Status Code و متدهایی مانند `POST`؛  برای هر درخواست یک اتصال TCP جدید ایجاد می‌شود.
- **HTTP/1.1:** اتصال پایدار (Persistent Connection)، هدر `Host` و قابلیت‌هایی مانند انتقال Chunked و مدیریت Cache.
- **HTTP/2:** استفاده از قالب باینری، Multiplexing چند درخواست روی یک اتصال TCP  .
- **HTTP/3:** استفاده از QUIC روی UDP، پشتیبانی از جریان‌های مستقل و کاهش تأخیر برقراری اتصال.

**چرا HTTP/3 از UDP استفاده می‌کند؟**

UDP به‌تنهایی قابلیت اطمینان و ترتیب تحویل بسته‌ها را تضمین نمی‌کند؛ اما QUIC این قابلیت‌ها را در لایه بالاتر پیاده‌سازی می‌کند. در نتیجه، گم‌شدن بسته‌های یک جریان لزوماً جریان‌های دیگر را متوقف نمی‌کند. همچنین QUIC با کاهش تعداد رفت‌وبرگشت‌های لازم برای برقراری اتصال، تأخیر را کاهش می‌دهد.

## سؤال ۲

**الف) تفاوت Stateless و Stateful**

در ارتباط Stateless، سرور اطلاعات مربوط به درخواست‌های قبلی هر کاربر را برای پردازش درخواست بعدی نگه نمی‌دارد. در مقابل، در ارتباط Stateful، وضعیت و اطلاعات تعاملات قبلی حفظ می‌شود و درخواست‌های بعدی می‌توانند به آن وابسته باشند.

**ب) HTTP در کدام دسته قرار می‌گیرد؟**

HTTP ذاتاً یک پروتکل Stateless است. برای مدیریت وضعیت کاربر، می‌توان از Cookie و Session یا توکن‌هایی مانند JWT استفاده کرد. به این ترتیب، اطلاعات لازم برای شناسایی کاربر یا ادامه تعامل میان درخواست‌ها حفظ می‌شود.

## سؤال ۳

**الف) توضیح چالش**

در HTTP معمولی، ارتباط با درخواست Client آغاز می‌شود و Server در پاسخ به آن اطلاعات ارسال می‌کند. بنابراین، سرور نمی‌تواند بدون درخواست قبلی، به‌صورت مستقیم پیام جدیدی را روی همان سازوکار معمول به Client ارسال کند. این محدودیت برای Webhook، چت و ارسال هشدارهای لحظه‌ای مشکل ایجاد می‌کند.

**ب) راهکارها**

**۱. Polling:** کلاینت در بازه‌های زمانی مشخص، درخواست‌های جدیدی برای بررسی اطلاعات به سرور ارسال می‌کند. این روش ساده است، اما درخواست‌های تکراری می‌توانند باعث افزایش سربار و مصرف منابع شوند.


**۲. Server-Sent Events (SSE):** کلاینت یک اتصال HTTP برقرار می‌کند و سرور می‌تواند از طریق همان اتصال، رویدادها را به‌صورت پیوسته برای کلاینت ارسال کند. این روش برای اعلان‌ها و به‌روزرسانی‌های یک‌طرفه مناسب است.

**۳. WebSocket:** پس از برقراری اتصال اولیه، یک ارتباط پایدار و دوطرفه ایجاد می‌شود که در آن کلاینت و سرور هر دو می‌توانند پیام ارسال کنند. این روش برای چت و ارتباطات بلادرنگ مناسب است.



## سؤال ۴

اجزای URL زیر را مشخص می‌کنیم:

`ss://asghar:1234!!@ss.myproxy.com:1234#shadowSocks1`

- **Scheme:** `ss`
- **Username:** `asghar`
- **Password:** `1234!!`
- **Host:** `ss.myproxy.com`
- **Port:** `1234`
- **Fragment:** `shadowSocks1`

## سؤال ۵

**۱. دیتابیس سایت مشکل پیدا کرده و درخواست‌های لاگین انجام نمی‌شوند.**

`503 Service Unavailable`

زیرا سرویس به‌صورت موقت قادر به پردازش درخواست‌ها نیست. اگر خطای داخلی عمومی و غیرمنتظره‌ای رخ داده باشد، `500 Internal Server Error` نیز مناسب است.
البته اگر نمیدونستیم دقیقا مشکل از دیتابیس است ارور ۵۰۰ مناسب است اما چون میدانیم پس ارور ۵۰۳ بهتر است.

**۲. نام کاربری واردشده وجود ندارد و لاگین موفق نیست.**

`401 Unauthorized`
زیرا کاربر باید احراز هویت کند و با برگرداندن این ارور میتونیم نشان ندهیم کاربر در دیتابیس وجود ندارد.

**۳. وب‌سایت به دامنه دیگری منتقل شده است.**

`301 Moved Permanently`

زیرا انتقال دائمی است و آدرس جدید از طریق هدر `Location` مشخص می‌شود.
البته اگر دائمی منتقل شده باشد. اگر موقت باشد از کد ۳۰۷ نیز میتوان استفاده کرد.

**۴. تعداد درخواست‌های کاربر از نرخ مجاز بیشتر است.**

`429 Too Many Requests`

زیرا کاربر از محدودیت نرخ درخواست‌ها عبور کرده است. در صورت نیاز، می‌توان زمان انتظار را با هدر `Retry-After` اعلام کرد.

**۵. درخواست تمدید JWT موفق بوده و توکن جدید در Header برگردانده شده است.**

`200 OK`

زیرا عملیات موفق بوده و پاسخ شامل توکن جدید در هدر مربوطه است.

**۶. کاربر از محدوده IP ممنوعه برای دسترسی به سرویس استفاده می‌کند.**

`403 Forbidden`

زیرا سرور درخواست را دریافت کرده، اما به دلیل محدودیت دسترسی اجازه انجام آن را نمی‌دهد.
تفاوتش با ۴۰۱ این است که میدانیم کاربر کی هست و اجازه دسترسی ندارد ولی در حالتی که کد ۴۰۱ برمیگردانیم، نمیدانیم کاربر کی هست.

## سؤال ۶

**۱. استفاده از سرورهای داخلی دانشگاه به‌جای سرورهای مرکزی برای دریافت بسته‌ها**

**Caching Proxy / Package Mirror**

سرور داخلی نسخه‌ای از بسته‌ها را نگه می‌دارد تا درخواست‌های بعدی از همان سرور پاسخ داده شوند. این کار مصرف پهنای باند اینترنت و بار سرورهای مرکزی را کاهش می‌دهد و سرعت دریافت بسته‌ها را افزایش می‌دهد.

**۲. تقسیم درخواست‌ها بر اساس مبدأ جغرافیایی درخواست‌ها**

**Reverse Proxy / Load Balancer با Geo-based Routing**

درخواست‌ها بر اساس موقعیت جغرافیایی کاربر به سرور مناسب هدایت می‌شوند. این روش می‌تواند تأخیر را کاهش دهد و بار درخواست‌ها را میان سرورهای مناطق مختلف توزیع کند.

**۳. اضافه‌کردن قابلیت احراز هویت برای یک سرویس بسیار قدیمی**

**Reverse Proxy به‌عنوان Authentication Gateway**

یک Reverse Proxy در مقابل سرویس قدیمی قرار می‌گیرد و پیش از ارسال درخواست به آن، احراز هویت کاربر را انجام می‌دهد. به این ترتیب، می‌توان قابلیت احراز هویت را بدون تغییرات اساسی در کد سرویس قدیمی اضافه کرد.
