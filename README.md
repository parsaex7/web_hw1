

سؤال ۱:

هر دو دستور برای ترکیب تغییرات شاخه‌های مختلف استفاده می‌شوند، اما روش کارشان متفاوت است.

دستور git merge تغییرات یک شاخه را با شاخه فعلی ترکیب می‌کند. در صورت نیاز، یک کامیت ادغام ایجاد می‌شود و تاریخچه شاخه‌ها قابل مشاهده باقی می‌ماند.

git switch main
git merge feature

در مقابل، دستور git rebase کامیت‌های شاخه فعلی را بر اساس آخرین وضعیت شاخه مقصد دوباره اعمال می‌کند. در نتیجه، تاریخچه معمولاً خطی‌تر و مرتب‌تر می‌شود، اما شناسه کامیت‌های بازسازی‌شده تغییر می‌کند.

git switch feature
git rebase main

به‌طور کلی، merge برای ادغام شاخه‌ها و حفظ روند تاریخی آن‌ها مناسب است؛ در حالی که rebase برای مرتب‌تر کردن تاریخچه کاربرد دارد. بهتر است از rebase روی شاخه‌هایی که دیگران نیز از آن‌ها استفاده می‌کنند، بدون هماهنگی استفاده نکنیم.

در merge ما تغییرات شاخه خودمون رو با تغییرات شاخه اصلی یکی میکنیم ولی در rebase اول تغییرات شاخه اصلی رو میاریم توی شاخه خودمون و از اول کامیت ها ساخته میشوند.

سؤال ۲: 

در خروجی دستور git diff، هر Hunk بخشی از تغییرات فایل است که به‌صورت یک قسمت جداگانه نمایش داده می‌شود. یک Hunk ممکن است شامل اضافه شدن، حذف شدن یا تغییر چند خط باشد.

دستور زیر امکان انتخاب قسمت‌های مختلف تغییرات را برای اضافه شدن به مرحله Staging فراهم می‌کند:

git add -p README.md

پس از اجرای دستور، Git هر بخش از تغییرات را نمایش می‌دهد و می‌توان مشخص کرد که آن بخش به Staging اضافه شود یا نه. برای مثال، گزینه y تغییر را اضافه می‌کند، گزینه n آن را رد می‌کند و گزینه s در صورت امکان یک Hunk را به بخش‌های کوچک‌تر تقسیم می‌کند.

این قابلیت زمانی مفید است که چند تغییر متفاوت در یک فایل انجام داده‌ایم، اما می‌خواهیم فقط بخشی از آن‌ها را در یک کامیت ثبت کنیم. به این ترتیب، کامیت‌ها منظم‌تر و هدف هرکدام مشخص‌تر می‌شود.

سؤال ۳:

دستور git bisect برای پیدا کردن کامیتی استفاده می‌شود که باعث ایجاد یک مشکل شده است. این دستور با جست‌وجوی دودویی، نسخه‌های مختلف پروژه را بررسی می‌کند و تعداد بررسی‌های لازم را کاهش می‌دهد.

ابتدا فرایند را شروع می‌کنیم و مشخص می‌کنیم که نسخه فعلی مشکل دارد:

git bisect start
git bisect bad

سپس آخرین کامیتی را که مطمئن هستیم در آن مشکل وجود نداشته است، معرفی می‌کنیم:

git bisect good <good-commit>

Git یک کامیت میانی را انتخاب می‌کند. پروژه را در آن وضعیت بررسی می‌کنیم و با توجه به نتیجه، یکی از دو دستور زیر را اجرا می‌کنیم:

git bisect good

یا:

git bisect bad

این کار را ادامه می‌دهیم تا Git کامیت مشکل‌ساز را مشخص کند. در پایان، برای بازگشت به وضعیت قبلی شاخه، دستور زیر را اجرا می‌کنیم:

git bisect reset

مزیت این روش آن است که به‌جای بررسی تک‌تک کامیت‌ها، محدوده جست‌وجو در هر مرحله کوچک‌تر می‌شود چون هر بار نصف میشود.

سؤال ۴: بررسی وضعیت فایل‌ها، ثبت کامیت و .gitignore

الف)

برای مشاهده وضعیت فایل‌ها و تفاوت تغییرات با آخرین کامیت، می‌توان از دستورهای زیر استفاده کرد:

git status
git diff
git diff --staged

دستور git status وضعیت فایل‌ها را نشان می‌دهد. دستور git diff تغییرات ثبت‌نشده در Staging را نمایش می‌دهد و git diff --staged تغییراتی را نشان می‌دهد که به Staging اضافه شده‌اند و آماده ثبت در کامیت هستند.

ب)

دستور git commit به‌طور معمول فقط تغییراتی را ثبت می‌کند که قبلاً با git add به Staging اضافه شده‌اند.

برای مثال، اگر ابتدا فایل README.md را به Staging اضافه کنیم و سپس آن را تغییر دهیم، تغییر جدید به‌صورت خودکار وارد همان کامیت نمی‌شود. در این حالت، تغییرات قبلی در کامیت ثبت می‌شوند و تغییرات جدید همچنان در Working Directory باقی می‌مانند.

ج)

برای اینکه Git پوشه tmp/ در ریشه پروژه را نادیده بگیرد، می‌توان الگوی زیر را در فایل .gitignore قرار داد:

/tmp/

وجود / در ابتدا باعث می‌شود این قانون به پوشه tmp/ در ریشه مخزن  باشد.

نکته مهم این است که .gitignore فایل‌هایی را که قبلاً توسط Git دنبال شده‌اند، به‌صورت خودکار از مخزن خارج نمی‌کند. اگر پوشه قبلاً Track شده باشد، می‌توان آن را از Index حذف کرد، بدون اینکه فایل‌های محلی پاک شوند:

git rm -r --cached tmp/
git commit -m "Stop tracking tmp directory"

سؤال ۵:

الف)

وقتی تغییرات دو شاخه با یکدیگر تداخل داشته باشند و Git نتواند به‌صورت خودکار تصمیم بگیرد که نتیجه نهایی چه باشد، تعارض یا Conflict رخ می‌دهد. برای مثال، ممکن است دو شاخه یک خط مشترک را به شکل‌های متفاوت تغییر داده باشند.

البته صرف تغییر یک فایل در هر دو شاخه الزاماً باعث Conflict نمی‌شود؛ اگر تغییرات با یکدیگر تداخل نداشته باشند، Git معمولاً می‌تواند آن‌ها را به‌صورت خودکار ادغام کند.

ب) تشخیص فایل‌های دارای تعارض

بعد از اجرای دستور Merge، می‌توان از دستور زیر برای مشاهده وضعیت مخزن استفاده کرد:

git status

Git فایل‌هایی را که نیاز به حل تعارض دارند، مشخص می‌کند. داخل این فایل‌ها ممکن است علامت‌هایی مانند نمونه زیر دیده شوند:

<<<<<<< HEAD
Current branch changes
=======
Incoming branch changes
>>>>>>> feature

بخش بالایی مربوط به شاخه فعلی و بخش پایینی مربوط به تغییرات شاخه‌ای است که در حال ادغام آن هستیم.

عکس نمیشد قرارداد این نمونه رو از چت گرفتم.

ج)

اگر لازم باشد تغییرات هر دو شاخه حفظ شوند، باید فایل دارای تعارض را باز کنیم و با توجه به هدف پروژه، محتوای نهایی را به‌صورت دستی تنظیم کنیم. ممکن است لازم باشد هر دو تغییر را نگه داریم یا آن‌ها را به شکلی مناسب با یکدیگر ترکیب کنیم.

پس از اصلاح فایل، تمام علامت‌های تعارض باید حذف شده باشند. سپس مراحل زیر را انجام می‌دهیم:

git status
git add README.md
git diff --check
git diff --cached
git commit

در این مثال فرض شده است که فایل دارای تعارض README.md است. اگر فایل‌های دیگری نیز درگیر باشند، باید آن‌ها را هم اصلاح و به Staging اضافه کنیم. با بررسی تغییرات آماده ثبت و اجرای کامیت، فرایند Merge تکمیل می‌شود. همچنین باید مطمئن شویم که هیچ علامت تعارضی در فایل‌ها باقی نمانده است.

د)

اگر پس از بررسی متوجه شویم که فعلاً نباید Merge انجام شود، می‌توانیم با دستور زیر فرایند ادغام را لغو کنیم:

git merge --abort

این دستور تلاش می‌کند مخزن را به وضعیت قبل از شروع Merge برگرداند. بهتر است قبل از شروع Merge، تغییرات محلی را ثبت یا ذخیره کنیم تا احتمال از دست رفتن تغییرات کاهش یابد.

سؤال ۶:

حالت اول:

فرض می‌کنیم فایل notes.txt قبلاً توسط Git دنبال شده، تغییرات آن هنوز به Staging اضافه نشده‌اند و می‌خواهیم فقط تغییرات همین فایل را دور بریزیم.

دستور مناسب:

git restore --worktree -- notes.txt

این دستور فایل را به وضعیت موجود در Index برمی‌گرداند. در این سؤال، چون Index با آخرین کامیت یکسان است، تغییرات ثبت‌نشده فایل حذف می‌شوند و فایل‌های دیگر دست‌نخورده باقی می‌مانند.

 این دستور تغییرات محلی فایل را از بین می‌برد؛ بنابراین قبل از اجرای آن باید مطمئن شویم که به این تغییرات نیاز نداریم.

حالت دوم: 

اگر تغییرات notes.txt را اشتباهی با git add به Staging اضافه کرده باشیم، اما هنوز کامیتی انجام نداده باشیم، می‌توانیم از دستور زیر استفاده کنیم:

git restore --staged -- notes.txt

این دستور تغییرات فایل را از Staging خارج می‌کند، اما محتوای ویرایش‌شده را در Working Directory نگه می‌دارد. در نتیجه، تغییرات از بین نمی‌روند و در صورت نیاز می‌توانیم بعداً آن‌ها را دوباره به Staging اضافه کنیم.

حالت سوم: 

فرض می‌کنیم یک کامیت اشتباه روی شاخه مشترک main ارسال شده و اعضای تیم نیز آن را دریافت کرده‌اند. چون نمی‌خواهیم تاریخچه مشترک را بازنویسی کنیم، استفاده از git reset یا Force Push انتخاب مناسبی نیست.

راهکار مناسب استفاده از git revert است:

git revert <commit-hash>

این دستور یک کامیت جدید ایجاد می‌کند که اثر تغییرات کامیت اشتباه را معکوس می‌کند. در نتیجه، کامیت قبلی از تاریخچه حذف نمی‌شود و اعضای تیم نیز می‌توانند تاریخچه مشترک را بدون نیاز به بازنویسی آن دنبال کنند.

با توجه به اینکه در صورت سؤال Working Directory تمیز است، می‌توان این دستور را اجرا کرد و پس از بررسی نتیجه، کامیت جدید را روی شاخه مشترک ارسال کرد.
